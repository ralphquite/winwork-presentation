# Codex — bootstrap проекта WinWork Guided Sales Demo

## Цель

Подготовить техническую основу веб-проекта **WinWork Guided Sales Demo** — интерактивного sales-инструмента для демонстрации WinWork корпоративным клиентам.

На этом этапе **НЕ нужно создавать дизайн презентаций, реальные слайды или копировать интерфейсы WinWork**.

Задача этого этапа — только:

- создать чистую и устойчивую frontend-архитектуру;
- подготовить проект к размещению трёх sales-маршрутов;
- настроить базовую навигацию между сценами;
- создать placeholder-компоненты для будущих `SlideScene`, `DemoScene` и `MediaScene`;
- подключить только действительно необходимые зависимости;
- настроить Git;
- подготовить GitHub-репозиторий;
- подготовить проект для деплоя на Vercel;
- оставить понятную структуру, которую можно будет постепенно наполнять дизайном из Pencil и интерактивными копиями WinWork.

---

# 1. Контекст проекта

Будет создано **одно веб-приложение**, внутри которого располагаются три варианта sales-презентации:

1. **Enterprise / Operations**
   - крупные компании;
   - логистика;
   - курьеры;
   - доставка;
   - склады;
   - ритейл;
   - большое количество исполнителей, объектов и сотрудников заказчика.

2. **API / Embedded**
   - компании, у которых уже есть собственные HR-, ERP-, staffing- или workforce-системы;
   - WinWork используется как инфраструктурный слой через API / White Label.

3. **Small Business**
   - небольшие компании;
   - сравнительно небольшое количество исполнителей;
   - основной сценарий — работа непосредственно через веб-кабинет WinWork;
   - акцент на простоте ежедневного использования.

Это **не три отдельных приложения**.

Нужно одно приложение и три маршрута:

```text
/enterprise
/api
/small
```

В дальнейшем маршруты могут переименовываться, поэтому не зашивать бизнес-логику глубоко в routing.

---

# 2. Формат будущей презентации

Будущая презентация представляет собой последовательность сцен.

Предусматриваются минимум три типа сцен.

## 2.1. SlideScene

Обычный презентационный экран:

- headline;
- текст;
- инфографика;
- графики;
- схемы;
- карточки;
- визуальные объяснения.

Позже дизайн будет переноситься из Pencil.

## 2.2. DemoScene

Интерактивная демонстрация интерфейса WinWork.

Это будет визуально точная frontend-копия нужного состояния реального продукта, но:

- без backend;
- без настоящей авторизации;
- без production/dev API;
- без реальных пользовательских данных;
- без зависимости от доступности WinWork;
- только с локальными demo fixtures;
- только с теми взаимодействиями, которые нужны для sales-flow.

## 2.3. MediaScene

Сцены для:

- видео;
- анимаций;
- демонстрации мобильного приложения;
- других media assets.

На bootstrap-этапе реализовать только минимальные placeholder-компоненты этих типов.

---

# 3. Ключевой архитектурный принцип

Презентация должна работать как **guided sales demo**, а не как свободная копия приложения.

В дальнейшем sales-менеджер должен проходить по заранее заданному маршруту:

```text
Slide
→ Slide
→ Demo
→ Slide
→ Demo
→ Video
→ Slide
```

Не нужно строить сейчас универсальный presentation editor, CMS или сложный slide builder.

Нужен небольшой, предсказуемый и расширяемый runtime.

# 4. Технологический стек

Использовать:

- React;
- TypeScript;
- Vite;
- React Router;
- Tailwind CSS;
- Motion / Framer Motion для будущих transitions и анимаций;
- Zustand только для небольшого presentation/demo state, если это действительно оправдано;
- Lucide Icons для временных системных иконок;
- ESLint;
- Prettier.

Использовать **актуальные стабильные совместимые версии** зависимостей на момент выполнения задачи. Не фиксировать версии из этого ТЗ, если они уже устарели.

### Не использовать без необходимости

Не подключать:

- Next.js;
- backend;
- database;
- ORM;
- authentication;
- API server;
- Redux;
- Storybook;
- shadcn/ui;
- Material UI;
- тяжёлую analytics-систему;
- тестовый framework, если без него bootstrap остаётся проверяемым;
- CMS;
- presentation framework вроде Reveal.js.

Если в процессе Codex обнаружит вескую техническую причину изменить этот список, сначала оставить объяснение в итоговом отчёте, но не усложнять архитектуру превентивно.

# 5. Package manager

Использовать **pnpm**, если он доступен в окружении.

Если pnpm отсутствует:

3. не блокировать работу только из-за отсутствия pnpm.

Зафиксировать используемый package manager через lock-файл.

# 7. Presentation config

Три презентации должны описываться данными, а не тремя независимыми реализациями.

Например, конфигурация может иметь такую идею:

```ts
type PresentationScene = {
  id: string;
  type: 'slide' | 'demo' | 'media';
  component: React.ComponentType;
  title?: string;
};

type PresentationConfig = {
  id: string;
  title: string;
  scenes: PresentationScene[];
};
```

Это только пример.

Codex может выбрать более корректную TypeScript-модель.

Главное:

- маршрут загружает presentation config;
- config определяет последовательность сцен;
- одна и та же сцена в будущем может переиспользоваться в нескольких презентациях;
- порядок сцен можно менять без переписывания движка.

---

# 8. Минимальный presentation runtime

На bootstrap-этапе достаточно реализовать:

- отображение текущей сцены;
- `Next`;
- `Previous`;
- переход по клавишам `←` / `→`;
- возможность перейти к сцене по её индексу или id внутри runtime;
- отображение текущего номера сцены только в dev/debug режиме;
- корректную работу browser Back/Forward там, где это не усложняет приложение;
- reset presentation state при начале презентации заново.

Не нужно сейчас делать полноценный UI управления презентацией.

### URL

Желательно предусмотреть возможность прямой ссылки на сцену.

Например:

```text
/enterprise?scene=intro
```

или иной простой механизм.

Но не усложнять routing вложенными URL для каждой сцены, если это не даёт пользы.

# 9. Placeholder content

Чтобы проверить архитектуру, создать для каждого маршрута несколько временных сцен.

Например:

```text
Enterprise
1. Intro Slide
2. Example Slide
3. Example Demo
4. Final Slide

API
1. Intro Slide
2. Architecture Slide
3. Example Demo
4. Final Slide

Small
1. Intro Slide
2. Example Slide
3. Example Demo
4. Final Slide
```

Это должны быть очевидные placeholders.

Не пытаться сейчас придумывать:

- реальные sales-тексты;
- настоящий дизайн;
- реальные возможности WinWork;
- интерфейсы WinWork;
- диаграммы;
- business claims.

Все placeholders должны легко удаляться позже.

---

# 10. Визуальная база bootstrap

На текущем этапе дизайн намеренно нейтральный.

Нужно только:

- viewport на весь экран;
- корректная работа на типичных desktop-разрешениях;
- чистый нейтральный фон;
- базовая типографика;
- простая центрированная placeholder-композиция;
- отсутствие декоративного «авторского» дизайна со стороны Codex.

Не пытаться самостоятельно создавать visual identity WinWork.

Позже реальный presentation design system будет получен из Pencil.

---

# 11. Responsive behaviour

Основной сценарий использования — desktop / laptop browser во время sales-встречи.

Приоритет:

```text
1920×1080
1440×900
1366×768
```

Приложение должно адекватно масштабироваться между распространёнными desktop viewport.

Мобильную версию самой sales-презентации сейчас проектировать не нужно.

При этом интерфейс не должен ломаться при более узком viewport.

---

# 12. Fullscreen

Предусмотреть простой механизм перехода презентации в browser Fullscreen через Fullscreen API.

Например:

- кнопка в dev/control overlay;
- клавиша `F`.

Не пытаться обходить browser restrictions.

Если браузер требует user gesture — это нормально.

---

# 13. Demo state

Подготовить место для будущих локальных fixtures:

```text
src/demos/fixtures/
```

Будущие DemoScene должны работать исключительно с демонстрационными данными.

На bootstrap-этапе достаточно одного простого примера локального объекта данных.

Не создавать abstractions для REST/GraphQL/API, потому что backend у presentation-demo не планируется.

---

# 14. State management

Не создавать глобальный store, если React state достаточно.

Если Zustand действительно нужен для runtime, разделить состояния концептуально:

```text
presentation state
demo scene state
```

Demo state одной сцены не должен случайно влиять на другую.

В будущем при повторном открытии demo-flow должна существовать возможность вернуть его в стартовое состояние.

---

# 15. Анимации

Подключить Motion / Framer Motion и создать только один минимальный пример перехода между placeholder-сценами:

- opacity;
- небольшой translate;
- короткая duration.

Не создавать сложную animation system сейчас.

Все реальные переходы будут определяться позже после дизайна презентации.

Также учитывать `prefers-reduced-motion`.

---

# 16. Accessibility и keyboard handling

Даже несмотря на sales-сценарий:

- кнопки должны быть настоящими `<button>`;
- обеспечить понятный focus;
- не перехватывать клавиатуру внутри input/select/textarea будущих demo-flow;
- `Esc` должен позволять выйти из fullscreen стандартным способом;
- навигация `←` / `→` не должна срабатывать, когда пользователь вводит данные в поле.

---

# 17. Error handling

Добавить простой application-level error boundary.

Если одна сцена падает, желательно показать понятное dev-friendly сообщение вместо полностью пустой страницы.

Не создавать сложную observability-инфраструктуру.

---

# 18. Environment variables

На bootstrap-этапе приложение не должно требовать никаких секретов.

Создать `.env.example` только в том случае, если действительно появляется хотя бы одна публичная environment variable.

Не создавать фиктивные env-переменные «на будущее».

Никакие API keys в repository не должны попадать.


Например:

```bash
git remote add origin <REPOSITORY_URL>
git branch -M main
git push -u origin main
```

Не выдумывать URL репозитория.

Проверить SPA routing так, чтобы прямое открытие:


При необходимости добавить минимальную Vercel configuration для SPA rewrite.

Не подключать Vercel к аккаунту и не создавать production deployment автоматически, если для этого требуется пользовательская авторизация или выбор team/project.

Пользователь будет отдельно настраивать Vercel после bootstrap.

# 28. Definition of Done

Этап считается завершённым, если:

- приложение запускается локально;
- существует один React/Vite проект;
- работают `/enterprise`, `/api`, `/small`;
- есть минимальный reusable presentation runtime;
- существуют три базовых типа сцен;
- presentation tracks задаются конфигурациями;
- есть placeholders для проверки архитектуры;
- нет backend и внешних runtime-зависимостей от WinWork;
- проект успешно проходит lint/typecheck/build;
- Git настроен;
- initial commit создан;
- GitHub настроен, если авторизация позволила это сделать;
- проект готов к ручному подключению к Vercel;
- архитектура позволяет далее без переделки начать перенос дизайна из Pencil и реализацию интерактивных WinWork demo flows.

После этого **остановиться и не приступать к созданию самой презентации**.
