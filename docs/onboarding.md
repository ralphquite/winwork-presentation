# Offline onboarding prototype

`/onboarding` is a separate protected catalog; `#tariff` opens commission reduction, `#topup` opens account top-up, `#company` opens company information, and `#marketplace` opens the first marketplace task. The landing page links to the catalog. It does not use presentation scene IDs or change existing Court/demo flows.

Build with `pnpm build:onboarding:offline`, then open `dist/offline/Открыть онбординг WinWork.html` directly. The same React components run in the web route and single-file artifact. Fonts, SVGs, CSS and JS are embedded; the offline CSP blocks network connections. No server or installation is needed.

The combined sales artifact (`pnpm build:sales:offline`, `dist/offline/Открыть продажи WinWork.html`) embeds the same catalog and all four scenarios. `OnboardingPrototype` accepts an optional `hashPrefix` (`/onboarding`) and `homeHref` (`#/`), producing `#/onboarding#tariff` etc. and a catalog link back to the three presentations. Standalone and web callers retain the original hashes and behavior.

## Scope and reference

The authorized WinWork dev interface was inspected on 2026-09-21: `/aggregator/start-page`, `/aggregator/my-tariff/tariff`, and the commission-reduction drawer. Layout, original SVG assets, Roboto/Montserrat fonts and form controls were recreated as semantic React UI. Company, balances, contacts, passport and payment details are synthetic. Other sidebar sections explain that they are outside this scenario. All three top-up banks are selectable using synthetic fixtures. The top-up invoice and QR entry are implemented locally.

Success was confirmed from the dev frontend's `commissionReductionApplication` success handler and shared info-dialog styles, without submitting a real request: “Заявка успешно отправлена”; “Спасибо! В ближайшее время с вами свяжется наш специалист.” Closing the confirmation also closes the drawer. The tariff banner remains available and the rate stays at 7%; this prototype does not simulate approval or guarantee 3%.

Every field, including citizenship, fills its fixed synthetic value on click or Enter/Space. Inputs are read-only: focusing with Tab alone does not fill them. Clicking the original selfie upload surface immediately adds a synthetic attachment marker, without a file chooser or access to local files. Repeated clicks are idempotent; deletion/re-attachment works. “Заполнить демо-данными” remains a bulk shortcut. Required-field/readiness validation still guards submission; the last field click or attachment advances to Send once the form is ready.

Product text fields, including the invoice amount, have no blue focus outline, matching the user-confirmed WinWork appearance. This scoped override does not change button/radio focus indicators or the onboarding target highlight.

## Company information

`#company` starts on the shared “Здравствуйте!” home screen: Settings → “Информация о компании” → fill the public profile → Save. Settings selects this tab by default, matching the source; the explicit tab click takes the guide to the public form. Four action steps follow the dismissible welcome. The profile starts with no brand name, logo or public details. Legal details remain synthetic and separate from this task.

The live `/aggregator/settings/company` screen was inspected on 2026-09-21. Its 900px cards, legal rows, 112px logo, external field labels, 56px inputs, 113px description, character counter and paired contacts are recreated as React. The empty building icon comes from the source; the attached logo is a bundled synthetic demo marker. Reviews start empty for this new demo company. The available dev frontend bundle's `savePublicProfile` handler confirms the success toast “Публичный профиль обновлён”; no profile was submitted on the source service.

Logo and all six fields fill fixed synthetic fixtures on click or Enter/Space. Tab does not fill fields; repeated clicks are idempotent, and logo removal/replacement works. Brand name is required to save, matching the source contract. Completing this onboarding additionally requires the logo and every requested field, then a successful local save. Saving a partially filled profile does not complete the guide. Company labels are above fields, unlike the floating labels in the tariff drawer. The tour is positioned outside the profile card when side space permits, leaving other fields accessible.

`winwork.onboarding.company.v1` stores only a version, page/tour checkpoints, fixture-field identifiers and boolean logo/completion flags. Readiness is rechecked on reload. Company reset does not touch tariff progress, and vice versa. Both the catalog and shared help list expose all four scenarios. Help restores guidance at the saved checkpoint, and leaving the settings page pauses the guide until resumed.

## First marketplace task

`#marketplace` starts on the shared home: Marketplace → “Разместить задание” → “Одиночное задание” → fill the form → “Создать задание” → open the new table row. Five action steps follow the dismissible introduction. The final card explains “Теперь исполнители будут откликаться” and points to “Отклики (0)”; the demo never receives or invents responses.

The authorized Dev session for ООО «Ф» was inspected on 2026-09-21. At the user's explicit request, a clearly marked synthetic task was created and its row/detail/empty responses tab verified. The source showed status “Создан”. Its street field remained invalid despite text entry; the live test was completed as remote work. The local demo supports both address and remote variants without reproducing that validation defect. The source date filter initially hid the future task; the demo starts with “За все время”. No source company identity or task identifier is copied into the runtime.

The 552px create drawer and 630px detail drawer reproduce the observed controls with semantic React, shared fonts/icons, and synthetic data. The company-only shell omits the project balance/project selector and Receipts item, as in the inspected company. Fields fill on click or Enter/Space; Tab alone does not change values. Region enables city; remote work hides address fields. “Добавить” adds a second work item; “Убрать” removes it. Each visible field (including demo optional details) plus at least one executor category is required for this teaching path. Count and payment type start with the source defaults. Read-only details reuse the same form and preserve the created values. PDF, registry editing, task actions/history are outside this bounded prototype and explain that when clicked.

`winwork.onboarding.marketplace.v1` stores only fixture field identifiers, selected built-in categories, booleans and page/tour checkpoints. Creation and completion are revalidated on reload; completion additionally requires opening the row. Repeated creation cannot duplicate the first task. Reset clears only this scenario. Closing the panel or leaving the page pauses guidance; help resumes it. The catalog and both older flows link to the new flow, with progress shown as four scenarios.

## Account top-up onboarding

`#topup` is second in both the catalog and help, immediately after commission reduction and before the first marketplace task. The tariff completion card offers “К пополнению счёта”; top-up completion offers “К первому заданию”. Each flow can also be opened independently.

Four action steps follow the dismissible introduction: (1) open “Мой тариф” and switch to “Пополнение”; (2) choose the shared bank and review the top-up methods; (3) fill the inline amount; (4) choose PDF/Excel and generate the invoice. Navigation and tab selection are two prompts within step 1. Step 4 highlights the format choices and generation button together. The guide follows actual actions, and returning through the sidebar preserves the current checkpoint. A 25,000-ruble amount is still filled on click or Enter/Space. Completion means **invoice prepared**, not money received: no payment is made and the balance remains zero. The final guide explains payment through the company's bank account. The main guide stays outside the bank-requisites/invoice form when space permits.

`winwork.onboarding.topup.v1` stores its own page/tour, bank fixture ID, format and boolean amount/prepared checkpoints. It never stores bank details or a custom amount. Stored schema version 3 uses `home`, `tariff`, and `topup` pages. The existing storage key stays stable; version 1 tariff/invoice checkpoints migrate to the new top-up tab, and version 1/2 records default to Т-банк without losing amount, format or prepared status. Bank selection persists across reload; switching bank preserves amount/format and clears invoice preparation. Resume restores the correct tab; reload checks that preparation requires a filled amount. Reset clears only top-up. Copy/download of ordinary requisites is optional and never completes this invoice teaching path. `bankRequisites.ts` owns all three synthetic bank fixtures and clipboard fallback; `topUpAssets.ts` maps each bank to its bundled QR, PDF/XLSX invoice and requisites PDF. These interactions also work on the shared tariff page in the commission flow.

Catalog cards are semantic articles with separate Open and “Сбросить флоу” buttons. Reset stays inside its own card, does not open a flow and does not reset other scenarios. Returning to the catalog restores focus to the last flow's Open button.

## Top-up invoice

The user-authorized redesign on 2026-09-25 splits “Тариф и пополнение” into “Тариф” and “Пополнение”. “Тариф” contains one full-width card: the left column has an enlarged commission application and document/check rates; the right column groups card, bank-account and SBP transfers. Both columns stretch to the same height. As refined on 2026-09-27, “Пополнение” has three cards: always-visible QR above the invoice form on the left, with copyable requisites on the right. A shared Т-банк / Банк Долинск / ТКБ selector sits in a full-width white card above both columns, using the same 24px padding and 8px radius as the other cards, and changes their QR, invoice downloads and requisites together. Bank selection uses native radios styled like the PDF/Excel format choices. The company-account warning sits immediately below the requisites heading; BIC/bank name and INN/KPP use paired rows, and both columns share the same height. The QR and other card headings use 22px, its description and the format legend use 16px. The QR demo caption and “Скачать повторно” button are removed; the prepared-file status remains. The invoice has no separate page, Back button or QR popover. Tabs expose tab/panel semantics and support ArrowLeft/ArrowRight/Home/End.

The commission and company-account notices share the existing pale-blue background and icon treatment. The introductory “Укажите сумму и выберите формат…” notice has been removed from the invoice card. The page retains Roboto/Montserrat and existing WinWork colors. Fresh Chrome inspection of the authorized dev page on 2026-09-25 confirmed Roboto for body text, rates and the ruble symbol; Montserrat for the main page heading and commission application button. The latter matches the source at 15px/500. The original bundled Latin/Cyrillic subsets lacked U+20BD, so tiny official Google Fonts ruble-only subsets of both existing families are now embedded with explicit unicode ranges. This fixes fallback rubles throughout the onboarding without changing the font families. Layout decisions also follow NN/g guidance on [tabs](https://www.nngroup.com/articles/tabs-used-right/) and [consistency](https://www.nngroup.com/articles/consistency-and-standards/).

In this deterministic demo, click the amount or press Enter/Space to insert 25,000 rubles. The permanent “Демо: нажмите на сумму” caption is removed; the optional guide describes the field action. Generate downloads the selected bank’s bundled PDF/XLSX fixture with matching synthetic requisites. Each QR contains only a distinct bank-specific non-payment demo marker. All assets are imported into the standalone HTML. Switching tabs preserves the invoice values. The commission guide hides while on “Пополнение”; returning to “Тариф” restores it. The top-up flow controls the same invoice component with independently persisted checkpoints. No real invoice or payment is created.

## Onboarding behavior

The first opening starts a dismissible introduction. Four action steps follow: open “Мой тариф”, open the application, fill the form and attach a selfie, then submit. Steps advance after the relevant local result. Cards sit beside measured target elements and recalculate on scrolling/resizing. “Назад” returns to the previous step. The notification bell comes first, followed by the training button and account selectors. The shared training button matches the adjacent account selectors: 32px height, white background, 8px radius and the same shadow. An 18px question icon, bold “Обучение” and regular-weight “N из 4” sit on one line. Its count uses the same completion flags as the help list, including the active flow’s current state, and updates after completion/reset. It opens “Первые шаги”, containing independent progress and resume/repeat for all four available flows.

The rules source is `prompts/onboarding-ux-rules.md`. Help and the form trap keyboard focus; Escape closes the uppermost layer or the active guide first. Narrow windows preserve an overflow-safe desktop canvas. Reset clears this scenario only.

`winwork.onboarding.tariff.v1` stores checkpoints and the names of fields matching built-in synthetic fixtures. Typed values, file names and file contents are never persisted. On reload, stored fixture fields are reconstructed and readiness is checked again. Dismissed guidance stays dismissed; help can resume it. When storage is unavailable, the scenario still works for the current opening. This persistence is specific to onboarding, separate from the mount-reset sales demos.

For adding another scenario, start with [the onboarding skill](skills/winwork-onboarding/SKILL.md). It captures the established workflow and exact extension points.
