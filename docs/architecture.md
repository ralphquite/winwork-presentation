# Архитектура bootstrap

## Поток данных

```text
URL track + ?scene=id
        ↓
PresentationConfig
        ↓
Presentation runtime
        ↓
SceneRenderer → SlideScene | DemoScene | MediaScene
```

Три sales-маршрута используют один runtime. Каждый файл в `src/presentation/config/` описывает только метаданные и порядок сцен. Renderer выбирается по discriminated union `PresentationScene`, поэтому новый track не требует нового движка.

## Состояние

- URL — источник истины для активной сцены. Это даёт прямые ссылки и работу Back/Forward.
- Runtime хранит только эфемерную ревизию, нужную для полного reset.
- `DemoScene` хранит своё состояние локально. Переход или reset размонтирует состояние, чтобы оно не протекало в другие сцены.
- Fixtures находятся только в `src/demos/fixtures/` и не имитируют сетевой слой.

## Как добавить сцену

1. Переиспользуйте существующий scene type и shared definition, если он подходит.
2. Добавьте data definition в нужный config.
3. Используйте уникальный стабильный `id` внутри track — он становится значением `?scene=`.
4. Не добавляйте бизнес-утверждения или дизайн, пока нет утверждённого источника.
5. Выполните `pnpm check` и проверьте маршрут в браузере.

Новый scene type допустим только тогда, когда `slide`, `demo` и `media` действительно не выражают требуемое поведение.

## Архитектурные запреты

- Никакого backend или production API.
- Никакой глобальной demo-state без обоснованной межсценовой потребности.
- Никаких отдельных React-приложений для sales tracks.
- Никакого CMS/editor слоя на bootstrap-этапе.
- Никаких реальных данных или секретов.
